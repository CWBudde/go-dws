## 4. Type-system triplication

Confirmed, and worse than the old PLAN.md described.

### 4.1 The `any` bridge

`internal/interp/types/type_system.go:553-559`:

```go
// Type aliases use 'any' to avoid circular dependencies with the interp package.
type ClassInfo = any       // Expected: *interp.ClassInfo
type RecordTypeValue = any // Expected: *interp.RecordTypeValue
type InterfaceInfo = any   // Expected: *interp.InterfaceInfo
type HelperInfo = any      // Expected: *interp.HelperInfo
type EnumTypeValue = any   // Expected: *interp.EnumTypeValue
```

Five of the fifteen `TypeSystem` registries (`type_system.go:22-41`) are therefore `ident.Map[any]`: `records`, `interfaces`, `helpers`, `enumTypes`, plus `classRegistry` whose entry is `Info any` (`class_registry.go:27`). The class registry API is entirely `any`-typed: `Register(name string, classInfo any)`, `Lookup(name) (any, bool)`, `LookupHierarchy(name) []any`, `GetAllClasses() map[string]any`, `FindDescendants(ancestorName) []any` (`class_registry.go:47,85,107,181,208`).

Two `func`-typed escape hatches complete the inversion: `ClassInfoFactory func(className string) ClassInfo` and `ClassValueFactory func(classInfo ClassInfo) any` (`type_system.go:38-39`), wired in `internal/interp/new.go:26-33`. `OperatorEntry.Class` is `interface{} // *ClassInfo (avoiding import cycle)` (`type_system.go:571`).

Every consumer type-asserts back. `e.typeSystem.LookupClass(...)` appears at 20 evaluator call sites, four of which assert to `runtime.IClassInfo` (`call_helpers.go:327`, `method_dispatch.go:374`, `runtime_ops.go:314`, and `runtime_ops.go:75` which keeps it as `classInfoAny`). Type-assertion counts in evaluator non-test code: `.(type)` 79, `.(*runtime.IntegerValue)` 57, `.(*runtime.StringValue)` 48, `.(*runtime.ArrayValue)` 48, `.(Value)` 44, `.(ObjectValue)` 41, `.(ClassMetaValue)` 37.

`any`/`interface{}` token counts (non-test): evaluator 135, runtime 84, interp 78, semantic 61, `internal/types` 30, `interp/types` 29, contracts 5, bytecode 6.

### 4.3 Type identity carried as strings

1. **The core value interface is string-typed.** `internal/interp/runtime/value_interfaces.go:8-13`:
   ```go
   type Value interface {
       Type() string   // "INTEGER", "STRING"
       String() string
   }
   ```
   There are 92 direct `.Type() == "…"` / `!= "…"` comparisons in non-test `internal/` code.

2. **Operator dispatch keys are `[]string` with an ad-hoc `"class:"` encoding.** `runtime.OperatorEntry.OperandTypes []string` (`runtime/class_interface.go:149`); `interptypes.OperatorEntry.OperandTypes []string` (`interp/types/type_system.go:573`). The encoder exists twice: `internal/interp/operators.go:136-160` ("All other types get a `class:` prefix") and `internal/interp/evaluator/runtime_ops.go:471-477,568` (`return "class:" + ident.Normalize(v.Class.GetName())`). The comparator is `internal/interp/operators.go:95-124`:
   ```go
   func areRuntimeTypesCompatibleForOperator(actualType, declaredType string, ts *interptypes.TypeSystem) bool {
       ...
       if strings.HasPrefix(normalizedActual, "array of ") && normalizedDeclared == "array of variant" { return true }
       if !strings.HasPrefix(normalizedActual, "class:") || !strings.HasPrefix(normalizedDeclared, "class:") { return false }
       actualClassName := strings.TrimPrefix(normalizedActual, "class:")
   ```
   The typed version already exists at `internal/types/operator_registry.go:100 areTypesCompatibleForOperator(actualType, declaredType Type)` and is not used on this path.

3. **Runtime metadata stores type names, not types.** 25 `*Name string` fields in `internal/interp/runtime`; the load-bearing ones: `ParameterMetadata.TypeName` (`metadata.go:25`), `MethodMetadata.ReturnTypeName` (`:79`), `FieldMetadata.TypeName` (`:158`), `ClassMetadata.ParentName` / `Interfaces []string` (`:203,205`), `EnumTypeValue.TypeName` (`enum.go:18`). `metadata_conversion.go:29,56,74,105,110` populates them with `fn.ReturnType.String()`, `param.Type.String()`, `decl.Parent.String()`, `intf.String()`, re-stringifying already-resolved AST type expressions, with `// Type will be resolved during semantic analysis` comments that never happen at this layer.

4. **`ExecutionContext` carries a string type context.** `runtime/execution_context.go:141-142`: `recordTypeContext string`, `currentFunctionReturnType string`, kept alongside the typed `recordTypeContextType *types.RecordType`.

5. **The evaluator re-parses type syntax from strings at runtime.** `evaluator/type_resolution.go:32 ResolveType(typeName string)`, `:93 resolveInlineArrayType(typeName string)`, `:168 resolveFunctionPointerType(typeName string)`, `:237 splitTypeList(s string)`, `type_resolution_helpers.go:164 parseInlineArrayType(signature string, ...)`.

## 8. Two compile pipelines

`internal/frontend` exists: 807 LOC in a single file, `internal/frontend/result.go`, exporting `Parse`, `ParseWithFilename`, `Compile(source, filename, hintsLevel)` and the internal `compileParsedResult` (`result.go:145,152,184,189`). Roughly 500 LOC of it is diagnostic normalization, ordering and filtering: `sortDiagnostics`, `diagnosticArgumentCountPriority`, `diagnosticStaticClassPriority`, `filterDiagnostics`, `normalizeSemanticDiagnostic` (`:236-736`). `internal/generics` exists: 423 non-test LOC (`clone.go`, `monomorph.go`).

**Non-test importers of `internal/frontend`: exactly one, `pkg/dwscript/dwscript.go`.**

**Finding 8.1.** `cmd/dwscript/cmd/run.go` (725 LOC) re-implements the pipeline by hand instead of calling `frontend.Compile`. `run.go:200-320`:

```go
l := lexer.New(input, lexerOpts...)          // :200
p := parser.New(l)                           // :203
program := p.ParseProgram()                  // :204
... errors.NewCompilerError / errors.FormatErrors ...   // :211-229
generics.Monomorphize(program)               // :235  "mirroring the shared frontend pipeline"
analyzer := semantic.NewAnalyzer()           // :263
...
interpreter := runner.NewWithOptions(...)    // :332
```

The comment at `run.go:233-234` ("mirroring the shared frontend pipeline") is an explicit admission of the fork. `cmd/dwscript/cmd` imports `lexer`, `parser`, `semantic`, `generics`, `bytecode`, `types`, `units`, `errors` directly; `pkg/dwscript` needs none of them because `frontend` encapsulates them.

**Finding 8.2.** The two pipelines are not behaviourally equivalent. The CLI skips semantic analysis entirely when the program uses units (`run.go:262`: `if typeCheck && !hasUnits`); `frontend.Compile` has no such bypass. The CLI formats diagnostics via `internal/errors.FormatErrors` (`run.go:227,290`) as colored, source-annotated blocks with a `Compilation failed with N error(s):` banner; the frontend has its own 500-line sort/filter/normalize layer that renders the DWScript `Syntax Error: … [line: N, column: M]` shape via `Result.DiagnosticStrings()` (`frontend/result.go:136`). Fixture output that depends on diagnostic ordering or format differs between the two.

**Finding 8.3.** The CI gate and the ground-truth report measure different pipelines:

- `internal/interp/fixture_test.go:541` → `frontend.Compile(source, pasFile, hintsLevel)` then `:607 New(&buf)`. This is what `testdata/fixtures/baselines.json` gates.
- `cmd/fixture-report/main.go:54` → `exec.CommandContext(ctx, cli, "run", pasFile)`, the CLI, i.e. the other pipeline.

This structurally explains the persistent gap between the two published numbers. Measured 2026-09-06: harness 863/1928 scored, CLI 733/1928, a 130-fixture gap; FailureScripts 103 (harness) vs 1 (CLI). The CLI emits the same diagnostics as the harness for most `FailureScripts` cases but in the pretty format, so the deficit there is formatting, not semantics. The remaining `*Fail` categories (InterfacesFail, OverloadsFail, GenericsFail, …) are at 0 in both runners, which is a genuine diagnostic-parity gap. See PLAN.md T1–T3 and F1–F8.

## 10. Refactoring candidates, ranked

Impact is scored against the failure breakdown recorded in `docs/history/CODEBASE_REVIEW_2026-07.md` §3 (65% front-end rejection, 15% wrong output, 11% runtime panic, 9% missing diagnostic envelope). The PLAN.md item IDs are given in brackets.

### Tier A: high impact, low risk

**A1. Unify the two compile pipelines: make `cmd/dwscript/cmd/run.go` call `frontend.Compile`.** [PLAN T1 / A1]
Evidence: §8. Impact: the CI gate and the ground-truth report measure the same thing; removes the whole "passes in the harness, fails in the CLI" class; directly serves the diagnostic-envelope bucket. Risk: low, `frontend` is already the tested path; the delta is diagnostic formatting, which fixtures show immediately. Cost: about 300 LOC deleted from `run.go`, 8 imports dropped from `cmd/dwscript/cmd`.

**A2. Single source of truth for the builtin-helper table.** [PLAN A2, guarded by T5]
Evidence: §9.6. Impact: attacks the front-end bucket head-on (helper methods the runtime supports but the analyzer rejects). Risk: low, mechanical; a table-driven test comparing the registry against `evalArrayHelper`'s switch is trivial. Cost: one shared table (in `internal/builtins` or `internal/types`), three call-site rewrites.

**A3. Delete the confirmed-dead residue.** [PLAN A3]
Evidence: §2.3 and §3.4. About 560 LOC plus the `internal/interp/runner` shim. Risk: very low, deadcode-confirmed; two tests (`variant_nil_test.go:144`, the `json_conversion` tests) go with them.

**A4. Correct the plan's architecture numbers.** Done by the 2026-09 PLAN.md rewrite; this document is the replacement evidence.

### Tier B: high impact, medium risk

**B1. Collapse the shell's duplicate `builtins.Context` implementation.** [PLAN A4]
Evidence: §6.3. `interp/builtins_context.go` (1046) + `builtins_collections.go` (554) + `functions_builtins.go` (166), about 1,766 LOC shadowing `Evaluator`'s implementation and `internal/builtins/register.go:628-634`. Reachable only through `Interpreter.EvalFunctionPointer` → `functions_pointers.go:17`. Impact: removes the last real second engine in the shell and a silent divergence class (a builtin behaving differently when reached via a function pointer). Risk: medium, `EvalFunctionPointer` is on the public `builtins.Context` surface and FFI depends on it; route it to the evaluator instead.

**B2. Delete one of the two type-resolution stacks.** [PLAN A5]
Evidence: §5.3. 965 evaluator LOC re-deriving types from strings at runtime while `ast.SemanticInfo` is already threaded through `contracts.EngineState.SemanticInfo`. Impact: attacks the wrong-output and panic buckets; runtime string re-parsing of `array of …` and function-pointer signatures is exactly where inline and anonymous types go wrong. Risk: medium-high, the evaluator resolves types in contexts the analyzer skipped (units, `-e` with `typeCheck` off). Needs A1 first so the analyzer runs unconditionally.

**B3. Retire or quarantine `internal/bytecode`.** [PLAN A11]
Evidence: §7. 12,925 non-test + 17,060 test LOC; 18 of 44 statement node types; `for`, `case` and classes fail to compile; 2,637 LOC of forked builtins; no verified speedup. Impact: removes about 30k LOC (21% of repo `.go` lines counting tests) and a permanent second value-model/builtin fork from every future value-model change. Risk: medium, `pkg/dwscript.CompileModeBytecode` and `dwscript compile` are public API. Options: delete both, move behind a build tag, or keep the flags and freeze the package. The owner decision of 2026-07-04 is "keep, unmaintained"; decide explicitly rather than let it rot.

### Tier C: highest impact, highest risk (the real fix)

**C1. De-`any` the type system.** [PLAN A6]
Move the runtime class/record/enum/interface/helper models out of `internal/interp` into `internal/interp/runtime`, and type the registries. Evidence: §4. The import cycle the `any` aliases exist to break is `interp/types → interp`, and it only exists because `ClassInfo` lives in `interp` instead of `runtime`. `runtime.IClassInfo` already exists (`interp/class.go:86: var _ runtime.IClassInfo = (*ClassInfo)(nil)`), so the interface seam is in place; only the struct needs moving. Impact: removes the two factory callbacks, about 200 type assertions, and the whole class of "wrong `any` shape at runtime" panics. Risk: high, touches `class.go` (1088), `class_declaration.go` (620), `type_declarations.go` (692), and 20 evaluator call sites. Do it after A3 and B1 shrink the shell. Sequencing: (i) move `ClassInfo` + `ClassValue` to `runtime`, (ii) type `ClassRegistry` as `ident.Map[runtime.IClassInfo]`, (iii) delete `ClassInfoFactory` / `ClassValueFactory`, (iv) repeat per concept (record → enum → interface → helper), (v) drop the 12 parallel AST maps on `ClassInfo`.

**C2. Replace string type identity with typed identity.** [PLAN A7]
Evidence: §4.3. Impact: operator overloading (`OperatorOverloadPass` baseline 5, `OperatorOverloadFail` 0) and generic/array-of-const compatibility depend entirely on this string algebra. Risk: high, and a strict consumer of C1. Start narrow: make operator-overload dispatch key on `types.Type` and delete `interp/operators.go:95-124`, then retire the `Value.Type() string` comparisons and the `*Name string` metadata fields.

### Also planned

- Move `semantic.ResolveOverload` / `SignatureDistance` into `internal/types` so `evaluator` stops importing `semantic` (§3.3). [PLAN A8]
- Derive the 231-case builtin switch in `semantic/analyze_builtin_functions.go:39` from the registry (§9.5). [PLAN A9]
- Move `currentContext` / `nodeContext` off the long-lived `Evaluator` into `ExecutionContext` (§9.4). [PLAN A10]

### Deliberately not recommended

- TODO/FIXME cleanup (§9.1, 27 total).
- Panic-to-error conversion (§9.2, panics are not control flow).
- Splitting `internal/interp/evaluator` god files by size alone. `visitor_statements.go` (1627) and `visitor_declarations.go` (1583) are cohesive visitor dispatch; splitting them before C1 just moves the type assertions around. `array_helpers.go` (1868) is the exception and should shrink naturally once A2 lands.
